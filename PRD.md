# Product Requirements Document (PRD): sensor-mesh

> ESP32 sensor firmware that publishes readings over MQTT, with a host-testable core.

Open work is tracked in [GitHub Issues](https://github.com/bamr87/sensor-mesh/issues) and as `status: planned` entries in [features/features.yml](features/features.yml).

## 1. Overview

Cheap sensors, real telemetry: ESP32 nodes read environment sensors and publish JSON over MQTT to a broker the fleet can observe.

## 1.1 Missions

Sensor Mesh's direction is to become the ultimate open home for all things open sensor telemetry — data, tools, resources and transparency, gathered in one place that anyone can inspect and reuse.

1. **Provide data, tools, resources and transparency for all stakeholders, embedded and IoT practitioners, and the general public.** Firmware authors, operators and anyone reading a room's sensors are first-class audiences. The aim is a shared, inspectable commons: the same firmware, the same JSON, and the same broker path for everyone.
2. **Let inexpensive ESP32 nodes read environment sensors and publish clear JSON over MQTT to a broker anyone can observe, with a host-testable core so firmware can be verified off-device.** Cheap hardware should still produce real, structured telemetry that can be tested without flashing a board first.
3. **Feed that telemetry into the fleet's observe and mobile surfaces, and keep a deployable broker on fleet-infra, so sensor data stays open, inspectable and reusable.** A reading should travel from the node to the people who need it without disappearing into a proprietary cloud.

These missions set the course; they do not claim the work is finished. They serve the PRD's learning-first path: ESP32 nodes, MQTT JSON, and a host-testable core that can feed fleet-observe, fleet-mobile and a broker on fleet-infra.

**Requirement**

- MR1: Constitution §1 states one direction statement and exactly three numbered missions, and the README and AGENTS.md taglines match that direction and link to constitution §1.

Feature [SMESH-008](features/features.yml) traces to requirement MR1.

## 2. Goals

- PlatformIO firmware for ESP32 publishing sensor readings over MQTT
- Host-testable payload/encoding core in portable C
- Bridge readings into fleet-observe dashboards

Non-goals (near term): production hosting, paid services, anything outside the roadmap below without a PRD change.

## 3. Users

- The maintainer, learning embedded c on esp32 (esp-idf/arduino), mqtt and iot messaging by building.
- Fleet agents (hub evolution loop, backlog fan-out, `evolve` lane) that grow the repo one reviewed PR at a time.
- Fleet tie-in: Feeds sensor metrics into fleet-observe and fleet-mobile; deployable broker on fleet-infra.

## 4. Requirements

Phases are the build order: an agent picks the earliest unserved requirement first.

### 4.1 Phase 1 — Foundation

- FR1: Portable C payload encoder producing JSON readings, with a host test
- FR2: PlatformIO project for esp32dev that builds

### 4.2 Phase 2 — Core

- FR3: Wi-Fi + MQTT publish loop with reconnect
- FR4: BME280 temperature/humidity driver

### 4.3 Phase 3 — Fleet integration

- FR5: OTA firmware updates
- FR6: MQTT → OTLP bridge into fleet-observe

### 4.4 Non-functional

- NFR1: CI (`.github/workflows/ci.yml`, the fleet standard gate) passes on every PR.
- NFR2: No secrets or credentials are committed; configuration comes from environment variables.
- NFR3: Autonomous lanes are off by default, open pull requests only, and never merge.
