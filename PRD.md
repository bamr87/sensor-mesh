# Product Requirements Document (PRD): sensor-mesh

> ESP32 sensor firmware that publishes readings over MQTT, with a host-testable core.

Open work is tracked in [GitHub Issues](https://github.com/bamr87/sensor-mesh/issues) and as `status: planned` entries in [features/features.yml](features/features.yml).

## 1. Overview

Cheap sensors, real telemetry: ESP32 nodes read environment sensors and publish JSON over MQTT to a broker the fleet can observe.

| Version | Date | Notes |
| --- | --- | --- |
| 0.1 | 2026-10-28 | Initial requirements and phased roadmap (repo foundation). |

## 2. Goals

- PlatformIO firmware for ESP32 publishing sensor readings over MQTT
- Host-testable payload/encoding core in portable C
- Bridge readings into fleet-observe dashboards

Non-goals (near term): production hosting, paid services, anything outside the roadmap below without a PRD change.

## 3. Users

- The maintainer, learning embedded c on esp32 (esp-idf/arduino), mqtt and iot messaging by building.
- Fleet agents (hub evolution loop, backlog fan-out, `evolve` lane) that grow the repo one reviewed PR at a time.
- Fleet tie-in: Feeds sensor metrics into fleet-observe and fleet-mobile; deployable broker on fleet-infra.

## 4. Requirements

Phases are the build order: an agent picks the earliest unserved requirement first.

### 4.1 Phase 1 — Foundation

- FR1: Portable C payload encoder producing JSON readings, with a host test
- FR2: PlatformIO project for esp32dev that builds

### 4.2 Phase 2 — Core

- FR3: Wi-Fi + MQTT publish loop with reconnect
- FR4: BME280 temperature/humidity driver

### 4.3 Phase 3 — Fleet integration

- FR5: OTA firmware updates
- FR6: MQTT → OTLP bridge into fleet-observe

### 4.4 Non-functional

- NFR1: CI (`.github/workflows/ci.yml`, the fleet standard gate) passes on every PR.
- NFR2: No secrets or credentials are committed; configuration comes from environment variables.
- NFR3: Autonomous lanes are off by default, open pull requests only, and never merge.
